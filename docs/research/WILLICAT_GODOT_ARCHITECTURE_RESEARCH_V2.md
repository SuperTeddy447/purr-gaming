# WilliCat Godot world-architecture research V2

Scope: Godot 4.7.2; research completed 2026-09-28. This is a world-authoring recommendation, not approval to migrate Home. The current playable Home remains the baseline.

## How the engine pieces fit together

- **Transform and drawing:** `Node2D` is the position/rotation/scale parent for visual, physics, and marker children. `CanvasItem` owns visibility, `z_index`, and `y_sort_enabled`; `Sprite2D` is only a renderer, never the source of semantic positions. A floor-contact root makes visual sorting and gameplay arrival agree. See [Node2D](https://docs.godotengine.org/en/stable/classes/class_node2d.html), [CanvasItem](https://docs.godotengine.org/en/stable/classes/class_canvasitem.html), [Sprite2D](https://docs.godotengine.org/en/stable/classes/class_sprite2d.html).
- **Reusable objects:** a `PackedScene` bundles the visual, collision, interaction area, anchors, and optional animation/FX mount points for one object. A level scene owns each instance's transform and per-instance ID. When editor scripts add children, the child's `owner` must be set to the edited scene root for persistence; GodotAI's node authoring did this in the connection test. See [scene instancing](https://docs.godotengine.org/en/stable/getting_started/step_by_step/instancing.html), [nodes and scene instances](https://docs.godotengine.org/en/stable/tutorials/scripting/nodes_and_scene_instances.html), [editor scripts and ownership](https://docs.godotengine.org/en/stable/tutorials/plugins/running_code_in_the_editor.html).
- **World data:** `.tscn` holds authored placement, subscene instances, navigation, and camera. Custom `.tres` Resources hold reusable typed definitions (asset contract, station capabilities, decor footprint, movement profile, room camera), not world coordinates that belong to the scene. Runtime save data records stable instance IDs plus deltas/state; JSON is an export/interchange format only when a non-Godot consumer requires it. See [Resources](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html).
- **Interaction:** `Marker2D` marks local target positions. `Area2D` plus `CollisionShape2D` provides real world hit/trigger volumes; `StaticBody2D` protects furniture footprint; `CharacterBody2D` moves characters. The area should call an object's local action interface or emit a signal, not own global gameplay state. See [Marker2D](https://docs.godotengine.org/en/stable/classes/class_marker2d.html), [Area2D](https://docs.godotengine.org/en/stable/classes/class_area2d.html), [CharacterBody2D](https://docs.godotengine.org/en/stable/classes/class_characterbody2d.html), [signals](https://docs.godotengine.org/en/stable/getting_started/step_by_step/signals.html).
- **Navigation:** `NavigationRegion2D` owns the authored walkable `NavigationPolygon`; `NavigationAgent2D` queries a path to a semantic destination's *current* global position. The navigation server does not move actors; the actor performs `move_and_slide()` each physics frame. Wait for the first physics sync before querying. Visuals and physics shapes do not automatically affect the navmesh; bake or author clearance explicitly. For strict cell movement, `AStarGrid2D` is viable. See [2D overview](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_introduction_2d.html), [agents](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationagents.html), [meshes](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationmeshes.html), [AStarGrid2D](https://docs.godotengine.org/en/stable/classes/class_astargrid2d.html).
- **Camera and animation:** room-owned `Camera2D` framing is separate from object geometry. `AnimationPlayer` should animate local visual/FX properties; `AnimationTree` is only needed when blending becomes complex. Neither should be an authority for marker identity or rewards. See [Camera2D](https://docs.godotengine.org/en/stable/classes/class_camera2d.html), [AnimationTree](https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html).
- **Editor automation:** `@tool` is appropriate for non-destructive gizmos, local footprint preview, and inspector validation; a full `EditorPlugin` is only justified after repeated authoring pain. Editor-authored mutations must be saved explicitly and should use undo support where possible. GodotAI can inspect/write/screenshot live scenes, but does not replace tests. See [running code in editor](https://docs.godotengine.org/en/stable/tutorials/plugins/running_code_in_the_editor.html).
- **Groups:** useful for discovery and diagnostics, not persisted object identity. Prefer stable instance IDs and semantic queries. See [Groups](https://docs.godotengine.org/en/stable/tutorials/scripting/groups.html).

## Seven level-authoring families

| Family | Position owner | Collision / anchors / navigation | Moving an object; reuse / saving | Illustrated-art fit |
| --- | --- | --- | --- | --- |
| A. Freeform `Node2D` level | Level child transform | Often separate level nodes unless disciplined; level navmesh | Fast one-room art direction, but detached anchors can drift; saves need per-node IDs | Excellent visually, weak reuse by itself |
| B. `PackedScene` object composition | Level owns instance transform, object owns local geometry | Object owns footprint/interaction/anchors; level owns shared navmesh | Moving root moves anchors; same scene in many cafés; save by instance ID + transform | Excellent |
| C. `TileMapLayer` world | Cell coordinate | TileSet can own collision/navigation/occlusion; scene collection can spawn objects | Paints large repeated maps quickly; tile/cell IDs serialize well | Good for repeatable floor/walls, restrictive for unique large paintings |
| D. Hidden logical grid + freeform visuals | Grid cell for occupancy, instance transform for display | Grid owns placement/path constraints; objects own local anchors | Strong deterministic decoration, but needs grid-to-art registration | Good if grid remains invisible |
| E. TileMap + PackedScene hybrid | TileMap cells for architecture, instance roots for objects | Tile nav plus object footprint/anchors; clearance synchronization needed | Efficient maps and reusable stations; two authoring surfaces | Good if floor architecture is tile-compatible |
| F. Zone/room subscenes | Room transform plus object instance transform | Room owns nav/camera/transitions; objects own local interaction | Reusable rooms and streaming; too-large rooms need subzones | Excellent for authored cafés |
| G. Data-driven placement | Placement record/asset ID | Runtime factory must construct all geometry and maintain editor preview | Procedural variants and saves are easy; hand-editing and visual review are harder | Useful as *derived* or procedural layer, not the primary editor workflow |

TileMapLayer offers fast cell painting and TileSet navigation/collision; scene tiles instantiate a full scene per painted tile and carry a higher overhead than atlases. Use that mechanism only when the object genuinely needs scene behavior. See [Using TileSets](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html) and [TileMapLayer](https://docs.godotengine.org/en/stable/classes/class_tilemaplayer.html).

## Farming / life-sim pattern, without copying a game's implementation

Worlds know landmarks because the map asset is authored data. `house`, `farm`, `barn`, `river`, `forest`, and `shop` are stable scene instances, region IDs, tile/cell ranges, or transition destinations, not features inferred from artwork pixels. A building instance owns its door marker and footprint; the room owns transitions and nav; furniture owns seat/rest/approach points; saves record stable IDs and changed transforms/occupancy. A future decoration system can add an **invisible placement grid** and reservation rules without forcing premium illustrated sprites onto visible tiles. This is an architecture inference from the official scene, Resource, TileSet, and navigation patterns, not a claim about proprietary game code.

## Object ownership result

- `CounterStation`: own VisualBack, FrontOccluder, collision/footprint, `WorkerIdle`, `CoffeeAction`, `OrderPoint`, `ServePoint`, `SteamFXAnchor`, and local interaction area. If the counter and espresso machine can be rearranged independently, `CoffeeAction` may instead belong to an `EspressoStation` subscene mounted on the counter; do not duplicate the anchor in both. A queue entrance or room-wide service lane remains level-owned.
- `TableRound`: own tabletop, pedestal, footprint/collision, and table approaches; do not automatically own an independently movable chair's SeatAnchor.
- `Chair`: own SeatAnchor and ApproachAnchor. If an authored booth seat is fixed to a table, make it a child instance of that table/booth scene.
- `CatBed`: own Rest/Sleep/Knead anchors and footprint; `Plant`: own SniffAnchor and footprint. Optional cat-under-table mount belongs to the table, not a world pixel constant.
- `Entrance`: own threshold/spawn/exit markers where tied to the door; the level/zone owns the destination café/room transition.

Lab A/B encode the minimal version of this ownership. They intentionally omit a production placement grid, navmesh obstacle baking, tap/door/state/economy logic, and art.
